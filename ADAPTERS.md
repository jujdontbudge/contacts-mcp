# Phase 1 adapter handoff

Implement `Channel` in `src/channels/channel.ts`, register it with `ChannelRegistry`, and pass that registry to `ContactsCore`. Call `core.ingest(event)` for inbound and synced outgoing events. External message IDs must be stable and globally unique within their channel, as specified. Supply `account_id`, remote conversation ID, sender handle and participants; include all group participants. Phone normalization defaults to US for national numbers; use E.164 for other countries. Account IDs default to `default` only for manually added handles.

The spec leaves numeric resolver weights open: exact = 1, prefix = 0.74, full query-token inclusion = 0.65, trigram Dice similarity × 0.59. Unknown senders create unlinked handles and similarity suggestions (score ≥ 0.3), never automatic links. `link_handle` requires the caller’s explicit exact-proof statement. Value edits preserve old/new raw values in the required edit-log reason field, avoiding extra schema columns.

A conversation-only send infers its person only when exactly one linked person participates; otherwise select a person ID. Without a channel, the most recent conversation selects it; absent history, a sole handle channel selects it, otherwise choose explicitly. Draft approval re-resolves and checks its stored person/handle/channel. Outgoing messages initially have an unknown (`null`) sender handle because `Channel.send` does not return the sending identity; ingest fills it from the canonical synced copy. Reconciliation retains message IDs and updates the outbox conversation link.

Adapter failures are stored as `failed` and are not automatically retried. A crash or local persistence failure after external send leaves `sending` for manual reconciliation, preventing blind duplicate sends. `approved` is recorded inside the transaction that reserves `sending`. Sync cursor scheduling and recovery are phase 3.

The future creator CRM adapter can store `creator-crm` links, show `list_drafts` in the existing dashboard approval inbox and invoke approve/reject; no parallel CRM or marketing-repo changes are needed.

## Instagram via Beeper Desktop (phase 4)

Register `createInstagramChannel()` from `src/channels/instagram.ts` with `registry.register(...)` before constructing `ContactsCore({ registry })`. Set `BEEPER_ACCESS_TOKEN`, optional `BEEPER_BASE_URL` (default `http://localhost:23373`) and `BEEPER_INSTAGRAM_ACCOUNT_ID` (otherwise exactly one Instagram account is required). Use that account ID on handles/targets. Desktop must remain running; new DMs need v4.2.808+. The MIT SDK is pinned to 6.0.0. Route sends through the core outbox for authorization and its existing 20/hour Instagram limit; that limit cannot guarantee freedom from network restrictions.

Sync auto-paginates API-visible history and retrieves all participants. The base64url cursor holds the account and per-chat timestamp/sort key. `Channel` has no cursor-output method: persist `getCursor()` after full sync, or use awaited `onCursor(cursor)` checkpoints, called when the consumer resumes **after** successful `core.ingest(event)`. Replay after interruption is safe. Sync buffers one chat and scans full history each time, resuming emissions rather than opaque HTTP pagination tokens. Older edits/backfills require a no-cursor rescan; Beeper does not guarantee complete history.

Live subscribes to all chats at authenticated `/v1/ws`, filters to the selected account and ingests hydrated `message.upserted` entries. Reconnect backs off from 1s to 30s; call cleanup on shutdown and supply `onError`. Reconcile via REST every five minutes because sockets have no durable replay. `client` and `socketFactory` support offline injection. Missing usernames/incomplete participants fail closed. Attachments are metadata-only, with complete payloads retained in `raw`.

New DMs start without message text, then verify exactly one non-self recipient matching the normalized username and no `cannotMessage`. Existing direct chats also verify identity; groups require an existing chat ID. Merged/foreign/read-only chats are refused. Sends support text/replies only. Message and reply IDs encode JSON `[chatID, messageID]`. Pending sends receive bounded confirmation reads (20 at 250ms intervals); uncertain writes are never retried. Reconcile failures manually before retrying.

Live checks remain: owner-approved account/token setup; actual usernames/participants and history pagination; new-DM creation without initial text; pending-to-canonical IDs/status; owner-only direct/group/reply sends; socket auth/events and Desktop restart. No setup or real send was performed. Synthetic SDK-typed fixtures cover offline mapping, pagination, cursor resume, refusals, confirmation and reconnect.
## Phase 5: Resend email adapter

`src/channels/email.ts` exports `createEmailChannel(opts)`, an injectable-fetch adapter with start-conversation, groups and CC/BCC capabilities. No SDK or new dependency is needed. Environment defaults are `CONTACTS_EMAIL_FROM` (required), `CONTACTS_EMAIL_REPLY_TO` (optional), `RESEND_API_KEY` (send) and `RESEND_FULL_API_KEY` (receive/read sent metadata). `accountId` defaults to `default`; send rejects another account. An outbound subject is required unless inherited from a stored reply. Adapter-level `EmailContent` adds optional `html` and `outbox_id`; phase 1 core/tool schemas do not yet forward those two fields.

Sync starts at the newest received page, follows `after=<last page ID>` backwards, stops before the supplied received-email ID, retrieves full bodies/headers, then emits oldest first. Persist the last successfully ingested event's `external_id` as the cursor. Empty polls keep the previous cursor. A missing/expired cursor causes a deduplicated backfill. Outgoing email is staged at send time rather than mixed into the received cursor stream.

Thread keys use the first References ID, then In-Reply-To, resolving known/stored ancestors before hashing an unknown root. Headerless threads fall back to normalized subject plus sorted visible participants. Persist and supply `lookupMessage(id)` for both Resend IDs and RFC Message-IDs so a resumed/restarted adapter can reuse the original conversation key. Incoming parent links resolve to the parent's Resend ID when known; otherwise they retain the RFC header ID. Participants are lowercased From/To/CC addresses; BCC is preserved per outgoing message but excluded from visible conversation participants. Direction compares the From domain exactly to the configured sender domain. Full provider content, HTML, headers and received attachment metadata remain in `raw`; downloading attachment bytes is outside this adapter.

Send uses the outbox ID verbatim as `Idempotency-Key`. Supply `getOutboxId(target, content)` or adapter-level `content.outbox_id`; missing/ambiguous dispatch context must fail before HTTP, never generate a random key. Reply headers use the stored actual RFC Message-ID and extend the parent's References. The provider-issued sent Message-ID is fetched after send and preserved in `raw.message_id`; a metadata retrieval failure still reports a successful send, but replies to that message are blocked until its RFC ID has been reconciled. Resend idempotency retention is 24 hours; this does not authorize blind retries of old outbox entries.

### Composed registration and dispatch bridge

`src/composition.ts` is now the shared CLI/stdio/HTTP composition. `configuredChannels` builds the selected registry, and `createContactsSystem` supplies the email bridge. Outbox dispatch hooks carry an explicit outbox ID in `AsyncLocalStorage`; no payload matching or guessed dispatch IDs are used. `lookupMessage` rebuilds stored ingest events by Resend ID or RFC Message-ID through core. The adapter's outgoing raw metadata carries `contacts_outbox_id` so buffered staging retries retain the original dispatch context.

`onSent` writes to core's durable `staged_outgoing` table. Core records the outgoing message and marks the outbox sent before the composition calls `flushSent()` and `core.reconcileOutgoing()`. Reconciliation checks the confirmed external ID, uses the existing `core.ingest` dedupe path and removes the staged event transactionally. Startup recovers committed sends with staged metadata. Entries whose outbox is still `sending` are retained for manual reconciliation, never resent automatically. A failure before durable staging remains in the adapter's process retry buffer; provider metadata that never reached disk before a crash still requires manual recovery. Reconciliation errors surface without changing an already-sent outbox to failed.

Creator-system connection: the future composition adapter in the marketing repo should reuse the creator dashboard's approval inbox for contacts outbox drafts, retain `creator-crm` person links, and feed reconciled email events into the existing reply/follow-up jobs. Creators keeps do-not-contact/deal decisions; contacts keeps identities and conversation history. This avoids another outreach tracker or direct coupling between sections.

Verified against official Resend docs on 2026-10-12: [sending](https://resend.com/docs/api-reference/emails/send-email), [received lists](https://resend.com/docs/api-reference/emails/list-received-emails), [received retrieval](https://resend.com/docs/api-reference/emails/retrieve-received-email), [sent retrieval](https://resend.com/docs/api-reference/emails/retrieve-email), and [pagination](https://resend.com/docs/api-reference/pagination). Offline fixtures contain only invented addresses/content; no live sends are permitted by these tests.
## TikTok — Zernio (phase 6, offline implementation)

`src/channels/tiktok.ts` exports `createTikTokChannel(opts)` implementing `Channel`, plus `getCursor()` and `getLastInboundAt(conversationExternalId)`. Options are `apiKey`, `accountId`, `baseUrl`, injectable `fetch` (the native fetch signature) and `clock`. Defaults read `ZERNIO_API_KEY`, `ZERNIO_TIKTOK_ACCOUNT_ID`, and `ZERNIO_BASE_URL` (default `https://zernio.com/api`). Auth is `Authorization: Bearer <key>`. No SDK or additional dependencies.

Registration is now wired by the shared composition; standalone adapter example:

```ts
import { createTikTokChannel } from "./channels/tiktok.js";
const tiktok = createTikTokChannel();
registry.register(tiktok);
```

Sync lists every conversation page with `accountId` and `platform=tiktok`, filters other accounts/platforms, fetches every message page with required `accountId`, and sorts each thread by timestamp and ID without assuming TikTok honors sort order. The opaque Zernio pagination cursors are forwarded verbatim. Partial account failures/skips and broken pagination throw instead of recording a successful empty sync. Unknown fields are retained in `raw: { conversation, message }`; invalid required IDs, timestamps and directions fail closed.

Cursor integration for the daemon owner: persist `tiktok.getCursor()` into the existing `sync_state` for this account after a successful sync. The composed sync runner calls the optional `Channel.getCursor()` after successful consumption and saves it for the configured account. A watermark is advanced only when the generator resumes after a yielded event (after ingestion). Interrupted/failed ingest therefore permits safe replay. The base64url JSON cursor carries version/account plus each thread's latest message time, all IDs at that timestamp, and last inbound time. Resume scans all thread pages but yields only unseen watermark/newer messages. A delayed historic message older than a saved watermark, or an edit to an older message, requires a reconciliation sweep with `sync()` without a cursor; core deduplicates stable IDs. Never reset the stored cursor on a failed run.

```ts
for await (const event of tiktok.sync(savedCursor)) core.ingest(event);
const nextCursor = tiktok.getCursor(); // save to the existing sync_state
```

`direction: in` and real `sent_at` timestamps are exactly what `OutboxService` queries for its 48-hour gate. No additional reply-window hook is needed. Stable identity uses `tiktok:user:<opaque TikTok user ID>` (case preserved). When returned, `@participantUsername` is also a participant handle; `participantName` is display text only. Core does not auto-link these two handles: attach them to the same person only with explicit exact-ID proof. The original participant fields remain in raw. Outgoing sender IDs are preserved; absent sender ID uses `tiktok:account:<Zernio account ID>`. Message IDs are `zernio:<encoded account>:<encoded conversation>:<encoded platform message ID>`, identically on send and sync, preventing cross-account/thread collisions in core's channel-wide unique key.

Send requires an existing remote thread, correct account/channel, direct conversation and supported content. There is no create-conversation call. Before POST it paginates current thread history and refuses absent/expired inbound (at 48 hours exactly) or ten outgoing messages since the latest inbound. This counts native human replies too; a new inbound resets the budget. Sends are serialized within one instance; Zernio/TikTok remain authoritative for concurrent processes, eventual history visibility and delivery. Text limit is 6,000 characters; one image must declare JPG/PNG MIME type; upstream enforces the 3 MB limit. Unsupported email fields, multiple/non-image media and undocumented quote replies are rejected. A successful send returns the original opaque target thread ID; the generic send docs warn some other platforms return a different stored conversation ID, so confirm TikTok's correlation live. Errors distinguish window closure, rate limits (including Retry-After), auth and other HTTP failures. Sends are never retried automatically; opaque failures or missing sent IDs require reconciliation before retrying.

## Instagram official API and transport composition

`src/channels/instagram-official.ts` exports `createInstagramOfficialChannel`. Its injectable native-fetch seam talks only to `https://graph.instagram.com`, using `IG_GRAPH_VERSION` (default `v25.0`) on data endpoints and bearer authentication. `/me?fields=user_id,username` resolves `IG_USER_ID` when omitted. `IG_ACCESS_TOKEN` must already be a long-lived Instagram User token. This implements Instagram Login, not the Facebook Login/Page-token route. Required permissions are `instagram_business_basic` and `instagram_business_manage_messages`.

`CONTACTS_INSTAGRAM_TRANSPORT=beeper|official|both` is composed by `configuredChannels` under the single `instagram` channel ID:

- `beeper` (default) preserves Desktop behavior and requires its existing token/account settings.
- `official` requires `IG_ACCESS_TOKEN`, `IG_APP_SECRET`, `IG_WEBHOOK_VERIFY_TOKEN`; `IG_USER_ID` is recommended. Its logical account key is that ID, or `official` when resolving `/me`. Keep the key stable after first ingestion; switching an omitted ID to a configured ID requires deliberate handle/cursor migration. It cannot start conversations or send groups.
- `both` requires both sets of credentials. Configure **the same ExcerLock professional account** in both services. Its logical contacts account stays `BEEPER_INSTAGRAM_ACCOUNT_ID`, preserving existing Beeper handles; the official message/IGSID namespace still includes the actual Meta account ID. `src/channels/instagram-transport.ts` owns only composition. New DMs and existing Beeper threads with no stored inbound use Beeper; groups use Beeper. Existing direct replies use official within 24 hours of the latest inbound. Expired replies are refused, without Desktop fallback. Explicit human support may use the seven-day tag. No fallback occurs after any official failure or uncertain write. Official resolves the target's proven scoped ID or exact username, and refuses missing/ambiguous API-visible conversations. A cold start needs a verified username, never an IGSID.

Official sync lists all conversation pages with `/{IG_USER_ID}/conversations?platform=instagram&fields=id,participants`, reads each conversation node's `messages.limit(N).after(cursor){id,created_time}`, and hydrates each message through `/{MESSAGE_ID}?fields=id,created_time,from,to,message,attachments`. At most **20 most-recent message details per conversation** are requested, including across pages. Pagination URLs are never followed; only bounded edge cursors are forwarded to the fixed Graph host. Messages emit oldest first. A versioned base64url cursor stores each API conversation's consumed IDs and last inbound timestamp; checkpoints follow successful consumption. A new pass rescans the latest 20, deduplicating IDs rather than interpreting opaque Graph pagination positions as durable watermarks. An interruption replays uncommitted events. Requests inactive for 30 days may disappear; this is partial recovery, not an inbox export. A webhook received between polls remains stored even if it later falls outside the latest 20.

Official conversation keys are `ig:<IG_USER_ID>:user:<IGSID>`, so webhook messages need no API conversation lookup and later polling reconciles the same thread. External message IDs are `ig:<IG_USER_ID>:message:<Meta message ID>` (components URI-encoded), identical for sync, send confirmation and webhook echoes. Stable handles are `igsid:<IG_USER_ID>:<IGSID>`; returned usernames are additional participant handles. Both remain unlinked until exact-proof identity review. Raw API/webhook payloads preserve origin and provider IDs; media URLs are stored as metadata, never downloaded. Unsupported shared/deleted content may have empty text; raw evidence remains available. Text sends support up to 1000 UTF-8 bytes. Quoted replies and outgoing attachments are explicitly refused in this initial transport.

`both` envelopes the independent child cursors and retains a legacy Beeper cursor when switching from `beeper`. Completed child progress survives a failure of the other child. Never write a naked Beeper checkpoint to the combined row. Incoming events use core's stable external-ID dedupe. The pinned public Beeper SDK exposes local message IDs, **not Meta message IDs**: do not pretend these are interchangeable or dedupe by text/time. An explicit `instagramBoth.getPlatformMessageId(event)` adapter can supply a provider-proven Meta ID when available; otherwise separate Beeper/official copies remain. No automatic fuzzy message/conversation merging is performed. Beeper's send confirmations keep local IDs; full outbound cross-source reconciliation needs a bridge-proven ID mapping, a known coverage gap.

### Send policy and human support

Core gates ordinary official drafts/approval at 24 hours, then official refreshes API-visible history immediately before every send and also consults persisted inbound webhook evidence. Outgoing phone/API messages never extend the window. Missing/future inbound timestamps and exact expiry boundaries refuse sends. No create-conversation API is called. Sends POST `/{IG_USER_ID}/messages` with `recipient.id=<IGSID>` and `message.text`; the returned `recipient_id` and `message_id` must confirm the target. Writes are never retried automatically.

The MCP `send_message` content metadata can explicitly request `{ "instagram_tag": "HUMAN_AGENT" }`. The tag is persisted in the outbox, rechecked at approval, and adds `messaging_type: "MESSAGE_TAG", tag: "HUMAN_AGENT"` to the official request with a **168-hour** ceiling. Beeper rejects this metadata. Use only for a real human answering the customer's own support inquiry, with Meta's Human Agent feature approved; never automated or promotional outreach. An approval alone does not make agent-written marketing eligible.

### Webhooks and long-lived tokens

The daemon handles `/webhooks/instagram` before MCP bearer authentication. Only this path bypasses bearer auth; `/mcp` retains its existing checks. GET requires `hub.mode=subscribe`, the exact `hub.verify_token=IG_WEBHOOK_VERIFY_TOKEN`, and returns `hub.challenge` as plain text. POST requires `X-Hub-Signature-256=sha256=<hex HMAC>` computed over the exact raw body using `IG_APP_SECRET`; comparison is constant time. Bodies over 1 MiB are refused, and unsigned/invalid signatures cannot ingest. Signed `object=instagram` entries are filtered to the configured account. Inbound messages and outbound `is_echo`/self-sender messages (including phone sends) ingest through core; reads/reactions/postbacks are ignored. Replay is idempotent. An ingest failure returns 500 for Meta retry, with a generic safe status error. There is no message-triggered auto-response.

The existing polling lifecycle calls `Channel.maintenance()` before each pass. Official maintenance refreshes weekly when due, coalesces concurrent refresh checks, and uses the **unversioned** `GET https://graph.instagram.com/refresh_access_token?grant_type=ig_refresh_token&access_token=...`. Core owns a private `channel_secrets` table (migration 3), with token and refresh timestamp scoped to the logical account. Refreshed tokens override the seed `.env` token on restart and never appear in MCP/status output or diagnostics. Protect the database and its backups as secrets; SQLite does not encrypt them. The initial seed is recorded locally on first use; the first automatic refresh is seven days later, avoiding refresh of a newly issued token before Meta's 24-hour minimum. Supply an unexpired seed with at least a week of validity. Offline/stopped daemons cannot refresh; expired tokens require reauthorization. To replace/revoke the stored credential, stop the daemon and remove that account's private `channel_secrets` row before supplying the new long-lived seed. Changing `.env` alone deliberately does not overwrite a refreshed credential.
